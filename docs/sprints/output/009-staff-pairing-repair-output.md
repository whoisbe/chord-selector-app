## Design chosen for the invariant

> For every `NoteGroup` returned by `findPhraseMatches`, each pitch's associated staff must equal the staff that pitch had in the source piece.

**Chosen: sort and dedupe `notes` and `staves` together, as paired tuples, inside `copyGroup`.**

```ts
function copyGroup(group: NoteGroup): NoteGroup {
  if (!group.staves) {
    return { ...group, notes: normalizeNotes(group.notes) }
  }

  const staves = group.staves
  const pairs = group.notes.map((pitch, index) => ({ pitch, staff: staves[index] }))
  const uniquePairs = Array.from(
    new Map(pairs.map((pair) => [`${pair.pitch}:${pair.staff}`, pair] as const)).values(),
  )
  uniquePairs.sort((left, right) => left.pitch - right.pitch)

  return {
    ...group,
    notes: uniquePairs.map((pair) => pair.pitch),
    staves: uniquePairs.map((pair) => pair.staff),
  }
}
```

Rejected alternatives and why:

- **Replace `notes`/`staves` with one array of `{ pitch, staff }`.** This is the option the loop spec itself calls cleanest, and it does make desync type-structurally impossible everywhere, not just in one function. Rejected because it changes the shape of the canonical `NoteGroup.notes: number[]` field, which `CLAUDE.md` lists as a frozen contract requiring an ADR to change, and would ripple into `PhraseQuery`, the ingestion script, the artifact renderer, `PhraseLookupTab.tsx`, and every existing test. That is a materially larger and riskier diff than the defect warrants, and the loop's own stop rule (`NEEDS_ARCHITECTURE_DECISION`) reserves exactly this kind of `NoteGroup`-shape change for a case where the invariant *requires* it — it doesn't; a same-function fix satisfies it.
- **Pitch-keyed staff map.** Rejected per the spec's own note: loses information if a pitch ever appears on both staves at once. Not observed in this piece today (see risk below), but the tuple approach costs nothing extra to avoid the assumption.
- **Drop `staves` from `copyGroup`'s output.** Rejected — defers the problem Loop 006 will hit, contrary to the spec's preference for a real fix now.

**Is desync now structurally impossible, or only test-enforced?** Both, with a caveat. Within `copyGroup` — the *only* place in the codebase that transforms a `NoteGroup`'s `notes` for output — desync is structurally impossible: pitch and staff are carried as one object through dedup and sort, so there is no code path where the two arrays are reordered independently. It is not impossible at the type level across the whole codebase: nothing stops a future function from being written that sorts `group.notes` alone without touching `group.staves`. `staffPairing.test.ts` is the backstop for that case. Closing that residual gap requires the `{ pitch, staff }[]` redesign rejected above, which needs an ADR — flagged as an open question below, not undertaken here.

## Risks and open questions

- **Residual gap in "structurally impossible."** `copyGroup` is the only place `NoteGroup.notes`/`staves` are transformed today, so the fix is complete for the current codebase, but a future function that reorders `notes` without `staves` in lockstep would reintroduce the class of bug. `staffPairing.test.ts` is the regression guard until/unless the `{ pitch, staff }[]` redesign is taken up under its own ADR.
- **Untested edge case: a pitch on two different staves in one group.** This piece has zero instances (verified: `dup-pitch instances diff staff: 0` across all 823 groups) so the dedup-on-`(pitch, staff)` behavior for that case is implemented (both survive as distinct entries) but not exercised by any assertion. If a future piece has genuine unison cross-staff doubling, the pairing logic handles it correctly by construction, but nothing currently proves it.
- **Standing note carried forward, not acted on:** this repo still has no TypeScript typechecking. `typescript` is not a declared dependency and `vite build` (check 2) only strips types — a green build is not type safety. Adding `tsc --noEmit` would require a dependency, which the standing contract forbids without an explicit decision. Loop 004 recorded this; still true.
